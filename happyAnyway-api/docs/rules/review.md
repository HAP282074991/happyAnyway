# 审查与交付规则

适用：代码/文档审查、任务收尾、规则调整及例外。各项实现规范以对应权威文件为准，本文定义审查过程与完成标准。

## REVIEW-01 审查顺序
1. 对照用户任务和验收，确认实际解决了问题且没有扩大范围。
2. 核对 [架构](../../ARCHITECTURE.md) 的归属与依赖、[开发规则](development.md) 的实现方式。
3. 涉及接口和数据时分别核对 [接口规则](api.md)、[数据库规则](database.md)。
4. 按 [测试矩阵](testing.md) 判断验证是否匹配风险，有无遗漏的失败或权限场景。
5. 检查文档、配置模板、未提交修改与交付说明是否一致。

## REVIEW-02 可维护性
- 留意重复业务判断、隐式副作用、循环依赖、全局可变状态和无用抽象。
- 不因个人风格要求无关重写；可选建议与实际缺陷分开报告。
- 关注配置默认值和权限范围，防止“仅本地可用”的实现被误认为生产可用。
- 业务规则变化应有需求依据；数据库字段变化应检查消费者。
- 自动检查只提供其覆盖范围的证据，不能以绿灯替代业务审查。
- 核对开发规则中的日志与注释要求：关键操作可定位、无敏感信息和重复噪声，注释解释职责与原因且与实现一致。

## REVIEW-03 完成标准
- 验收条件满足，相关变更集中且可以解释。
- 适用验证已执行并报告结果；必需验证缺失时标记“实现完成、验证未完成”，不能声称全部完成。
- 必要文档、配置示例、契约或迁移同步。
- 不存在已知未处理的阻断缺陷；剩余可接受缺口列出影响和下一步。
- 更新 [交接](../HANDOFF.md)，复杂任务更新计划并在完成后归档。
- 是否提交、推送、发布按用户授权和现有流程执行，不把自动提交作为默认完成条件。

## REVIEW-04 规则调整与例外
- 明确要改变哪条规则、原规则为何不再适用、影响及替代验证。
- 在权威文件中更新规则，不只改检查实现或在局部添加豁免。
- 临时例外记录适用范围、原因、退出条件和下一步；不使用覆盖全仓的忽略项代替局部处理。
- 若涉及用户明确确定的架构或业务决定，先指出冲突并取得所需澄清；其余授权范围内的常规实现判断直接处理。
- 新规则若检查尚未实现，在质量状态中标记“人工审查”，不伪装为自动门槛。

## REVIEW-05 结果表达
交付时说明：改了什么、为什么、验证命令/结果、未验证项及影响。
发现问题时给出具体位置、触发条件、实际影响和修复方向；不以模糊“可能不好”作为阻断结论。
不得声称多个 Agent 独立审查过，除非实际发生；本项目不默认启动额外 Agent。

## REVIEW-06 持续执行
当前没有 CI 或分支保护，因此本地检查还不是强制合并门槛。
后续 CI 应运行对应检查并保存报告；在真实接入前保留人工交付核对。
