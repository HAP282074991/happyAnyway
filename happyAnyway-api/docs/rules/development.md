# 开发规则

适用：Java、Spring 配置、依赖和重构。本文定义实现方式；层级依赖以 [架构](../../ARCHITECTURE.md) 为准，数据和接口分别见 [数据库规则](database.md)、[接口规则](api.md)。
状态：本版规则用于后续开发；自动执行范围以 [质量状态](../quality.md) 为准。

## DEV-01 开发前
- 找到对应需求和验收条件，明确输入、输出、权限、错误场景。缺少会影响业务正确性的决定时先记录待确认事项，继续不依赖该决定的工作。
- 检查已有实现与未提交改动，优先沿用现有约定。不能把示例用户、订单等模块当成已批准需求。
- 跨层或多阶段改动按 [计划约定](../exec-plans/README.md) 留下可接续记录。

## DEV-02 代码组织与命名
- 使用架构规定的目录，模块名称在各层保持一致，Java 包名小写。
- 类名表达职责，如 UserController、UserService、UserMapper、UserEntity、UpdateNicknameRequest、UserProfileResponse；名称只是示例，不提前创建这些类。
- 使用构造器注入，必需依赖尽量 final；避免字段注入和通过全局容器主动查找业务依赖。
- 所有业务 Service 统一采用接口与实现类，即使只有一个实现也遵守。接口命名 XxxService，实现命名 XxxServiceImpl；目录见架构文档。
- 接口声明业务能力，实现类使用 implements 实现接口并注册为 @Service；业务逻辑及适用的事务注解放在实现类中。
- Controller 和其他调用方通过构造器注入 Service 接口，不直接注入或实例化 XxxServiceImpl。确有多个实现时显式选择，不能依赖不明确的默认装配。
- 该约定用于业务 Service，不要求工具类、Mapper 或配置类机械增加接口；不额外引入无需求的通用 BaseService。
- 不使用反射、ApplicationContext、静态服务定位等方式绕过层级限制。
- 不机械规定行数；出现多个独立职责、过多分支或重复业务知识时按职责拆分。

## DEV-03 业务与事务
- Service 组织用例；入口参数校验之外，仍检查业务前置条件与数据访问权限。
- 修改状态时明确合法转换、重复调用及并发结果，不能只“先查再写”而忽略竞争。
- 事务围绕必须原子完成的数据库操作；确认 Spring 代理调用与回滚条件，不能假定同类自调用会建立新的事务。
- 避免在持有数据库事务时等待外部 HTTP 或长任务。外部副作用与数据库原子性不一致时，明确失败恢复策略，不宣称一个本地事务覆盖外部服务。
- 只对满足幂等或可恢复条件的操作做有界重试；记录次数与退出条件，禁止无限重试。
- 不在数据库失败时自动切成假数据或内存结果并报告成功。

## DEV-04 异常与日志
- 新增或修改业务功能时必须同时考虑日志，在关键状态变更、外部调用失败、重试耗尽和异常处理边界添加必要记录；无需给每个 getter、Mapper 调用或方法进出打印日志。
- 使用 SLF4J 的 Logger/LoggerFactory 和参数化占位符，不使用 System.out、System.err 或 printStackTrace；不为日志单独引入尚未确定的 Lombok。
- INFO 记录有排查价值的重要业务结果，DEBUG 用于开发诊断，WARN 记录可恢复的异常状态，ERROR 记录未恢复的系统失败。普通参数错误和预期业务拒绝不默认打印 ERROR 堆栈。
- 日志应包含操作、必要的非敏感业务标识、结果；涉及耗时和外部调用时补充耗时及错误分类。requestId 链路能力接入后统一关联，当前不得假定已存在。
- 业务成功日志必须符合实际提交状态，不在可能回滚时宣称持久化完成；需要事务提交后的结果时选择相应执行时机。
- 捕获异常必须有处理目的：恢复、补充上下文或转换为稳定业务错误；不吞掉异常、不用空集合掩盖系统故障。
- 保留异常原因；接口错误表达按接口规则。避免每层重复打印同一异常。
- 日志描述操作和必要上下文，不输出密码、令牌、完整请求体或敏感资料；用户输入先限制长度并避免日志注入。
- 新增异步代码时说明错误如何被观察、资源何时释放；不能把异常藏在无人检查的 Future 中。
- 不默认记录 SQL 参数、完整 Entity/DTO、请求响应体；对必要用户输入做脱敏、长度限制和换行处理。高频循环和健康检查避免重复 INFO 日志。
- 系统异常在负责处理的边界记录必要堆栈，上层继续传播时保留 cause，不逐层重复记录；日志中不得包含凭证或敏感上下文。

## DEV-07 注释与说明
- 新增或修改的类、接口应有简洁中文 Javadoc，说明职责；业务 Service 接口方法、Controller 接口方法、Mapper 方法应说明业务含义及必要的参数、返回值、限制和异常。
- Service 接口说明调用契约，实现类说明实现职责；覆盖方法可用 @Override 和 {@inheritDoc} 复用契约，仅补充特有实现信息，不复制两份易漂移的说明。
- Entity、DTO 字段需说明业务含义；尤其明确单位、枚举值、时间语义、是否可空等不能从名称准确判断的内容。
- 对复杂分支、状态转换、并发处理、事务边界、特殊 SQL 和兼容处理添加注释，解释原因、约束及关联规则，而不是逐行翻译代码。
- 简单私有方法和访问器不强制重复注释；注释不能代替清晰命名和合理拆分。
- 修改实现时同步更新相关注释，删除失效注释；不保留大段注释掉的旧代码。TODO 写清缺口、原因及后续处理条件，不写无依据的作者或日期占位。
- 本规则用于后续新增及修改范围；现有基础代码的注释与日志完善另按实际需要处理，不因规则变更宣称已完成全仓补齐。

## DEV-05 配置与依赖
- 配置变化更新模板和运行说明；必需参数缺失时明确失败，不能静默连向别的环境。
- local 仅用于无数据库开发，不能与 mysql 混用，也不能作为生产配置。
- 新依赖说明用途、现有库为何不够、版本兼容与维护代价；不使用动态版本。关键版本沿用 pom/BOM 管理。
- 避免无关依赖升级和全仓格式化。密钥通过环境配置注入，示例只写占位值。
- 当前不要求添加 Redis、队列或微服务；需要时先记录具体问题及取舍。

## DEV-06 可维护性与收尾
- common 只放真正通用的能力，不作为跨模块访问的中转站。
- 删除或替换实现时检查引用、配置、测试和文档；不顺手改动无关行为。
- 验证按 [测试规则](testing.md) 执行，结果按 [审查规则](review.md) 交付。
- 允许提出更好的规则；不能在实现中悄悄引入与文档不同的约定。
