# 变更与版本协作
- 修改已确认需求时说明原因、变化内容和受影响验收项，评估前端、后端、数据和旧客户端。
- 不覆盖掉影响分析，只留下最新结论；重要跨端决定进入 decisions。
- 前后端各自 specs-reference.json 固定采用的规格提交和功能编号；规格更新不代表实现自动完成。
- bootstrap-unpinned 仅允许工程初始化与讨论；正式功能下发前建立提交版本。
- 任务消息包含功能编号、规格提交、接口版本、修改范围、依赖和验收。无权访问规格时报告缺失，不猜测。
- 双方发现规格问题向协调者反馈，公共规格统一修订，各端不复制并私改业务规则。
- 分别记录实现、联调、验收状态。跨工程变更按兼容顺序交付，不假设多个客户端同时升级。
- 不把 git pull 当作自动批准新需求；采用新版本需评估受影响内容。
