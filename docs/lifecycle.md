# 项目生命周期与干净基线

项目先完成架构，再开发业务。当前阶段由 [project-state.json](project-state.json) 标识；执行过程记录不属于可复用架构资产。

| 阶段 | 目标 | 检查与放行 |
|---|---|---|
| architecture | 工程骨架、目录与依赖边界、岗位规则、接口约定、检查器、CI、清理机制 | 骨架构建和规则正反用例通过；验证空记录基线可运行；用户验收架构。没有业务需求和业务测试不算架构缺陷 |
| ready | 架构验收后清理所得的干净基线 | 无筹备任务、报告、岗位实例、历史权限豁免和本机路径；保留规范、模板和代码；不自动开始业务开发 |
| development | 在干净基线上确认需求并实施 | 创建基线提交、确认需求与验收、逐岗初始化、登记任务；检查任务权限、版本和交付证据 |

## 长期保留与阶段清理

- 保留：工程代码与基础测试、依赖锁文件、目录约定、岗位配置、协作流程、架构／API／数据库规范、模板、检查器、CI。
- 清理：筹备任务及派工消息、执行计划与测试报告、岗位创建／接手历史、正式任务 ID、本机路径、旧规则回执、历史迁移豁免、过时组织决定。
- 重置：进度为“架构就绪，尚未开发”；运行登记为空；岗位等待重新初始化；各端需求引用仍为 bootstrap-unpinned，不能伪造业务规格批准。
- 正式架构决定保留其有效结论；过时决定和执行过程归入筹备记录，不能将旧组织方式带入基线。

稳定规则在 `docs/agents/automation-policy.json`，只含角色配置入口和允许范围；配置摘要在 `docs/agents/versions.json`，不含身份和本机位置。实际身份、规则接收和本次例外在 `docs/tasks/runtime.json`，与任务和证据一起清理。岗位配置的存在不代表岗位已创建或用户已确认初稿。

## 架构验收清单

- [ ] 两端基础工程及统一检查可运行，架构规范与现有骨架一致。
- [ ] 规则正反用例能发现预期错误；空任务、空岗位实例不会使基础检查失败。
- [ ] 清理预览没有筹备记录、失效链接和环境绑定，基础检查通过。
- [ ] 区分架构能力、尚待验证的基础能力与未来业务功能，不为填清单提前开发业务。
- [ ] 用户确认架构验收；之后才执行实际清理与建立开发基线。

没有真实业务就无法进行的业务联调、业务数据库用例和真机业务验收，进入开发计划。若架构本身承诺真实数据库基础连通或某种强制检查，仍须验证或如实说明未验证，不能用阶段划分冒充完成。

## 清理预览与正式收尾

```powershell
node scripts/baseline.mjs --plan
node scripts/baseline.mjs --preview .reports/baseline-preview
```

预览只向一个不存在的新目录复制有效资产并使用重置模板，绝不修改源项目或删除当前记录。目标目录已存在则失败，不覆盖、不递归删除。预览副本的 ready 状态用于测试零记录启动，不代表源项目已通过架构验收。重复预览使用新的目录名。

两端 specs-reference.json 使用清理清单中的模板重置为 bootstrap-unpinned、revision=null、features=[]；ready 检查拒绝旧需求引用。生命周期测试用独立夹具准备各阶段，不更改实际项目阶段，也不绕过预览工具对 development 的拒绝。

清理清单见 [baseline-manifest.json](baseline-manifest.json)，可逐项审核。清理前应确认架构结论已写入长期规范，所有执行任务已停止，没有需要保留的业务工作。架构验收通过后，按同一清单清理源工作树，或采用验证后的干净副本作为开发起点；清理结果重新运行完整检查。当前工具只提供清单和预览，实际清理在用户架构验收后执行。

清理是清除工作树中的过程记录，不重写 `.git` 历史，不删除聊天任务，不自动提交、推送或发布。开发阶段不得通过改回 architecture／ready 或删除记录绕过开发门禁。

## 开发启动

1. 确认干净基线并按用户授权建立 Git 基线提交。
2. 更新阶段为 development，确认业务需求与验收，锁定规格提交。
3. 在实际运行环境读取根项目经理身份；逐个确认并初始化所需岗位，把身份和配置回执写入运行登记。不能复制筹备期的 ID。
4. 用模板登记新任务，执行派工校验后再下发；交付证据对应实际源码。开发历史在开发阶段保留，返工追加依据。
