# 部门协作流程 V1

状态：2026-09-11 项目负责人已确认，作为统一执行流程。岗位按工作职责划分，不按目录数量划分；规则生效不代表任务已创建或工程已验收。

## 岗位与交付边界

| 岗位 | 接收什么 | 负责什么、交付什么 | 工作边界 |
|---|---|---|---|
| 项目经理（根任务） | 用户目标、各岗位反馈 | 明确范围，拆分任务、安排资源与进度，处理变更，汇总交付并组织用户验收 | 维护项目进度；不以管理确认代替独立审核和测试 |
| 产品设计 Agent | 已明确的目标、范围和约束 | 梳理用户场景、业务规则、页面交互与异常状态，形成需求设计和可验证的验收条件 | 维护 docs/requirements；业务取舍由项目经理汇总给用户决定，不自行扩大范围 |
| 后端开发 Agent | 已确认需求设计、接口约定和开发任务 | 实现后端、数据库及接口，编写相关测试、自检，提交实现说明 | 修改获派的 happyAnyway-api 范围，配合联调并修复缺陷 |
| 微信开发 Agent | 已确认需求设计、接口约定和开发任务 | 实现页面交互与客户端逻辑，编写相关测试、自检，提交实现说明 | 修改获派的 happyAnyway-wechat 范围，配合联调并修复缺陷 |
| 审核 Agent | 需求依据、待审版本及改动说明 | 独立检查需求符合度、架构、代码质量和遗漏，输出结论及具体整改项 | 可读取相关文档及两端实现；本岗位以审阅为主，不直接修复待审业务代码 |
| 测试 Agent | 验收条件、测试版本、运行方法和审核结论 | 设计用例，验证主流程、异常及跨端行为，记录缺陷、复测与测试结论 | 可运行授权环境中的检查、编写或维护获派测试；不修改业务逻辑来让测试通过 |

目标共六个岗位任务：当前项目经理加五个独立任务。按[创建与接手登记](agent-init.md)逐岗确认职责和边界后创建，未登记就绪的岗位不能视为已到位。审核、测试与开发分别承担责任；开发自检不能替代另两个岗位的结论。工具、设计素材、设备或真实环境缺失时说明缺口，项目经理协调解决。

## 从需求到验收

| 步骤 | 主责与协作 | 交付和放行条件 |
|---|---|---|
| 1. 明确目标 | 项目经理与用户沟通 | 明确目标、做与不做、约束及优先级；关键业务未知项不能当作已确认决定 |
| 2. 产品设计 | 产品设计主责，开发评估可行性，测试检查验收条件是否可验证 | 需求、交互、异常和验收条件齐全；项目经理提交用户确认范围与关键业务取舍 |
| 3. 分配开发 | 项目经理拆任务和排期，开发对齐接口 | 任务有负责人、范围、版本、依赖和验收条件；正式业务开发前锁定根需求提交并同步各端引用 |
| 4. 实现与自检 | 后端、微信按依赖并行开发，产品设计解答规格问题 | 可运行成果、实现说明、自检结果及未验证项齐全，再交审核 |
| 5. 独立审核 | 审核 Agent 审阅指定版本，开发整改 | 明确通过、需整改或阻塞；整改项经复审关闭，剩余风险明确后交测试 |
| 6. 独立测试 | 测试 Agent 验证，开发支持真实联调和修复 | 验收条件逐项有结果与证据，缺陷修复后复测；环境缺失记为未验证，不冒充通过 |
| 7. 汇总验收 | 项目经理汇总，用户验收 | 提供演示、审核与测试结论、剩余风险；用户决定通过、退回或有条件通过 |
| 8. 移交复盘 | 项目经理组织，各岗位补齐资料 | 记录交付版本、运行说明、遗留事项及负责人；更新进度与适用规则 |

产品设计阶段即可准备测试用例、开展技术评估，不必等到开发结束。正式测试结果必须对应实际交付版本；审核后又改动代码，受影响部分须复审并复测。验收通过不等于已授权发布。

## 交接与问题回流

- 所有岗位由项目经理统一调配。任务说明包含编号、目标与范围、负责人、交付物、依据版本、依赖、预计完成时间、反馈节点和验收条件；无法估算时说明原因。
- 交接只需要讲清：交付物在哪里、对应哪个版本、做了什么、验证了什么、还有什么问题、下一步交给谁。未提交内容明确标注，并提供可核对的改动范围；避免多个任务同时修改同一文件。
- 实现问题：审核或测试提出具体位置／复现步骤、预期与实际结果及影响，项目经理交回对应开发；审核问题由审核复审，测试缺陷由测试复测。
- 需求歧义：回产品设计澄清；影响已确认范围、优先级或业务取舍时，由项目经理交用户决定，再同步文档、任务和受影响用例。
- 关键阻塞或预计延期及时反馈，其他不受影响的授权工作继续。完成情况以证据为准，分别记录实现、自检、审核、测试及用户验收状态。
- 有条件验收需写明未完成条件、影响、责任人和处理安排，不能把未通过项改记为通过。

## 岗位交付的最小记录

- 产品设计：目标与边界、用户流程、适用页面状态、数据和权限规则、异常场景、验收编号及待确认项。简单功能放一份需求文件，不为形式拆多个空文件。
- 开发：需求版本、修改范围、接口变化、运行步骤、自检命令与结果、未验证项，注明待审提交；未提交则给出基线提交和可复核的差异清单。
- 审核：记录审阅者与被审版本，结论为通过／需整改／阻塞；问题写明文件或需求位置、触发条件、影响和处理建议。需求覆盖、架构边界、权限及数据处理、测试遗漏按实际范围检查，不以格式偏好阻断交付。
- 测试：记录执行者、需求和代码版本、环境、步骤、预期、实际、证据；每项验收条件标为通过／失败／未验证／不适用（附理由）。缺陷记录复现方式、影响、修复版本及复测结果。
- 项目经理：将上述实际报告位置、当前状态、阻塞责任人和下一步记入项目进度。报告可直接位于任务交付消息，结论必须可追溯，不能仅登记“完成”。

岗位不是文件权限隔离工具。实际接单先确认角色和可写范围；审核角色不兼任本次改动的开发，测试角色不把自身编写的业务实现作为独立验证。不同工作副本交接时明确提交或差异来源，不能假设对方已看到本地未提交修改。共用工作目录时同一文件串行修改。

## 文档与当前阶段

需求与设计使用 docs/requirements，每项功能优先用一份文档包含需求、交互与验收；项目总进度使用 docs/progress.md。开发说明在所属工程，审核和测试结论记录在对应任务交付报告中，由进度记录链接，不预先创建成套空目录或模板。

当前仍先完成 Harness 并验收，再开发业务。此阶段产品设计梳理工程使用与协作要求，开发完善工程机制，审核检查规则和实现是否一致，测试验证检查命令与协作交接是否实际有效；不为了演练新增业务模块。
