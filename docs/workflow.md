## 从需求到验收

| 步骤 | 主责与协作 | 交付和放行条件 |
|---|---|---|
| 1. 明确目标 | 项目经理与用户沟通 | 明确目标、做与不做、约束及优先级；关键业务未知项不能当作已确认决定 |
| 2. 产品设计 | 产品设计按[岗位配置](agents/product-designer.md)提供需求方案，开发评估可行性，测试检查可验证性 | 用户已明确确认方案选择，需求、交互、异常和验收条件齐全；未经确认不得进入开发实施 |
| 3. 分配开发 | 项目经理拆任务和排期，开发对齐接口 | 任务有负责人、范围、版本、依赖和验收条件；正式业务开发前锁定根需求提交并同步各端引用 |
| 4. 实现与自检 | 后端、微信按依赖并行开发，产品设计解答规格问题 | 可运行成果、实现说明、自检结果及未验证项齐全，再交审核 |
| 5. 独立审核 | 审核 Agent 审阅指定版本，开发整改 | 明确通过、需整改或阻塞；整改项经复审关闭，剩余风险明确后交测试 |
| 6. 独立测试 | 测试 Agent 验证，开发支持真实联调和修复 | 验收条件逐项有结果与证据，缺陷修复后复测；环境缺失记为未验证，不冒充通过 |
| 7. 汇总验收 | 项目经理汇总，用户验收 | 提供演示、审核与测试结论、剩余风险；用户决定通过、退回或有条件通过 |
| 8. 移交复盘 | 项目经理组织，各岗位补齐资料 | 记录交付版本、运行说明、遗留事项及负责人；更新进度与适用规则 |

产品设计阶段即可准备测试用例、开展技术评估，不必等到开发结束。正式测试结果必须对应实际交付版本；审核后又改动代码，受影响部分须复审并复测。验收通过不等于已授权发布。

## 交接与问题回流

- **先记录，再下发，每次派工都留痕。** 所有新任务、补充要求、返工、审核、测试、转派和恢复执行指令均适用，不因工作小或口头沟通省略记录。
- 发送前在 docs/progress.md 的任务下发记录中保存：任务编号、本次下发序号、时间、下发者、接收岗位及正式任务 ID、完整拟发送内容，并标为“待发送”。内容须含下述任务字段；同一任务的补充和返工追加新条目，不覆盖原指令。
- 发送消息必须带任务编号和记录位置。发送后补记实际发送结果及消息标识（工具提供时）；失败记为“发送失败”，结果不确定记为“待核实”，核实前不盲目重发。只有明确送达才记为“已发送”，接单确认与完成状态另行记录。
- Agent 接单时核对记录、版本和依赖；没有可访问的派工记录先反馈项目经理补齐，不凭零散聊天或旧指令执行。初始创建消息若同时包含工作任务，也须先登记派工；纯岗位创建与背景交接仍记在 agent-init.md。
- 所有岗位由项目经理统一调配。任务说明包含编号、目标与范围、负责人、交付物、依据版本、依赖、预计完成时间、反馈节点和验收条件；无法估算时说明原因。
- 交接只需要讲清：交付物在哪里、对应哪个版本、做了什么、验证了什么、还有什么问题、下一步交给谁。未提交内容明确标注，并提供可核对的改动范围；避免多个任务同时修改同一文件。
- 实现问题：审核或测试提出具体位置／复现步骤、预期与实际结果及影响，项目经理交回对应开发；审核问题由审核复审，测试缺陷由测试复测。
- 需求歧义：回产品设计澄清；影响已确认范围、优先级或业务取舍时，由项目经理交用户决定，再同步文档、任务和受影响用例。
- 关键阻塞或预计延期及时反馈，其他不受影响的授权工作继续。完成情况以证据为准，分别记录实现、自检、审核、测试及用户验收状态。
- 有条件验收需写明未完成条件、影响、责任人和处理安排，不能把未通过项改记为通过。

岗位不是文件权限隔离工具。实际接单先确认角色和可写范围；审核角色不兼任本次改动的开发，测试角色不把自身编写的业务实现作为独立验证。不同工作副本交接时明确提交或差异来源，不能假设对方已看到本地未提交修改。共用工作目录时同一文件串行修改。

## 文档与当前阶段

需求与设计使用 docs/requirements，每项功能优先用一份文档包含需求、交互与验收；项目总进度使用 docs/progress.md。开发说明在所属工程，审核和测试结论记录在对应任务交付报告中，由进度记录链接，不预先创建成套空目录或模板。

当前仍先完成 Harness 并验收，再开发业务。此阶段产品设计梳理工程使用与协作要求，开发完善工程机制，审核检查规则和实现是否一致，测试验证检查命令与协作交接是否实际有效；不为了演练新增业务模块。
