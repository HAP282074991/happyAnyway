# 部门协作流程

流程版本：WF-V3-20260915。本文件规定项目架构、干净基线交付及业务开发的跨岗位协作流程。

## 架构先行与阶段切换

阶段以 [project-state.json](project-state.json) 为准，具体步骤见[生命周期与清理](lifecycle.md)。

- architecture：搭建工程骨架、岗位规则、接口约定、检查器及 CI；保留筹备记录以便修复和架构验收。没有业务任务、实际岗位实例或数据库业务用例不构成架构缺陷。架构涉及的真实数据库基础能力等验证单独列明，不冒充已通过。
- 用户验收架构后：清理筹备过程记录，保留确认后的架构资产；重置进度、身份、派工和报告。先生成独立预览并验证，不提前清除源记录。
- ready：干净基线，零业务任务、零岗位绑定、零历史豁免，基础检查可运行；不是正在开发。
- development：确认需求与验收、初始化实际岗位、登记运行身份后，再按以下流程派工。业务联调、数据库用例、真机与发布验证随业务任务执行。

下文记录“只追加保留”的要求适用于当前阶段内的执行历史；架构验收后的清理是用户明确要求的阶段收尾例外。Git 历史不在清理范围。稳定配置只保存规则与版本；身份、接收回执和例外登记在 `docs/tasks/runtime.json`，不能写入长期策略。

## 从需求到验收

| 步骤 | 主责与协作 | 交付和放行条件 |
|---|---|---|
| 1. 明确目标 | 项目经理与用户沟通 | 明确目标、做与不做、约束及优先级；关键业务未知项不能当作已确认决定 |
| 2. 产品设计 | 产品设计按[岗位配置](agents/product-designer.md)提供需求方案，开发评估可行性，测试检查可验证性 | 用户已明确确认方案选择，需求、交互、异常和验收条件齐全；未经确认不得进入开发实施 |
| 3. 分配开发 | 项目经理拆任务和排期，开发对齐接口 | 任务有负责人、范围、版本、依赖和验收条件；正式业务开发前锁定根需求提交并同步各端引用 |
| 4. 实现与自检 | 后端、微信按依赖并行开发，产品设计解答规格问题 | 可运行成果、实现说明、自检结果及未验证项齐全，再交审核 |
| 5. 独立审核 | 审核 Agent 审阅指定版本，开发整改 | 明确通过、需整改或阻塞；整改项经复审关闭，剩余风险明确后交测试 |
| 6. 独立测试 | 测试 Agent 验证，开发支持真实联调和修复 | 验收条件逐项有结果与证据，缺陷修复后复测；环境缺失记为未验证，不冒充通过 |
| 7. 汇总验收 | 项目经理汇总，用户验收 | 提供演示、审核与测试结论、剩余风险；用户决定通过、退回或有条件通过 |
| 8. 移交复盘 | 项目经理组织，各岗位补齐资料 | 记录交付版本、运行说明、遗留事项及负责人；更新进度与适用规则 |

产品设计阶段即可准备测试用例、开展技术评估，不必等到开发结束。正式测试结果必须对应实际交付版本；审核后又改动代码，受影响部分须复审并复测。验收通过不等于已授权发布。

## 交接与问题回流

- **先记录，再下发，每次派工都留痕。** 所有新任务、补充要求、返工、审核、测试、转派和恢复执行指令均适用，不因工作小或口头沟通省略记录。
- 发送前在 docs/tasks/ 对应任务文件的派工历史中保存：任务编号、本次下发序号、时间、下发者、接收岗位及正式任务 ID、完整拟发送内容，并标为“待发送”。内容须含下述任务字段；同一任务的补充和返工追加新条目，不覆盖原指令。
- 发送消息必须带任务编号和记录位置。发送后补记实际发送结果及消息标识（工具提供时）；失败记为“发送失败”，结果不确定记为“待核实”，核实前不盲目重发。只有明确送达才记为“已发送”，接单确认与完成状态另行记录。
- Agent 接单时核对记录、版本和依赖；没有可访问的派工记录先反馈项目经理补齐，不凭零散聊天或旧指令执行。
- 所有岗位由项目经理统一调配。任务说明包含编号、目标与范围、负责人、交付物、依据版本、依赖、预计完成时间、反馈节点和验收条件；无法估算时说明原因。
- 交接只需要讲清：交付物在哪里、对应哪个版本、做了什么、验证了什么、还有什么问题、下一步交给谁。未提交内容明确标注，并提供可核对的改动范围；避免多个任务同时修改同一文件。
- 实现问题：审核或测试提出具体位置／复现步骤、预期与实际结果及影响，项目经理交回对应开发；审核问题由审核复审，测试缺陷由测试复测。
- 审核意见被指出有误或存在正确性争议时，项目经理在对应任务文件记录争议意见、相关版本、证据和待裁决问题，明确提示用户需要人类干预。暂停争议项及依赖它的放行，不盲目修改、不自行关闭争议；用户裁决后记录结果并安排后续工作，不受影响的授权任务继续。
- 需求歧义：回产品设计澄清；影响已确认范围、优先级或业务取舍时，由项目经理交用户决定，再同步文档、任务和受影响用例。
- 关键阻塞或预计延期及时反馈，其他不受影响的授权工作继续。完成情况以证据为准，分别记录实现、自检、审核、测试及用户验收状态。
- 有条件验收需写明未完成条件、影响、责任人和处理安排，不能把未通过项改记为通过。

## 长期岗位执行约定

- **接单确认**：Agent 收到派工后确认任务编号、文件范围、依据版本、依赖和交付要求，有歧义先反馈。项目经理将“已发送”“已接单”“执行中”分别记录；接单不代表已开工，无法读取材料时不得假定已经理解任务。
- **排队与插单**：每个岗位默认一次执行一个任务，其余排队。项目经理在用户已确认的优先级内安排顺序；插单前记录原任务暂停位置、成果版本和剩余事项，通知 Agent 并核实已暂停后再切换。恢复任务也须先记录再下发，接单时重核最新版本；改变用户确定的优先级须由用户决定。
- **配置版本凭据**：岗位配置内容变更时使用新版本标识，并在岗位登记中保存文件路径、Git 提交或未提交差异来源、带算法标识的规范化内容 SHA-256、变更摘要。另行记录该岗位最后确认的版本与摘要；未确认当前版本时标为“历史接手完成／最新规则待确认”，受影响工作不得开工。旧版本凭据和确认记录只追加保留。
- **变更通知**：需求、接口或岗位配置按权限批准变更后，项目经理记录新旧版本、变化内容、受影响任务和岗位，明确各任务继续、暂停或返工，并主动发送通知、记录接收确认。影响任务范围、权限或执行方式的通知按派工规则留痕；未确认接收前，不假定 Agent 已采用新版本，受影响的实施或放行保持暂停。
- **中断与接替**：中断时保留最后成果版本、未完成项、阻塞与下一步。项目经理核实旧任务及相关写入进程已停止处理该工作，接手者确认材料与范围后才恢复执行；不能仅凭无回复判断已停止。同一任务不得由两个 Agent 重复执行，工作中断与接替情况记录在对应任务文件中。

岗位不是文件权限隔离工具。实际接单先确认角色和可写范围；审核角色不兼任本次改动的开发，测试角色不把自身编写的业务实现作为独立验证。不同工作副本交接时明确提交或差异来源，不能假设对方已看到本地未提交修改。共用工作目录时同一文件串行修改。

## 摘要与派工凭据

- 配置和流程采用 sha256-utf8-lf-v1：严格按 UTF-8 解码，忽略文件开头的一个 UTF-8 BOM，仅把 CRLF 转成 LF，再以 UTF-8 编码计算 SHA-256。不删除空格、空行或末尾换行，不改写单独 CR。无效 UTF-8 报错。
- 在根目录运行 `node scripts/config-digest.mjs docs/agents/product-designer.md docs/workflow.md`；输出包含路径、算法和摘要。接收方对派工指定的实际文件运行同一命令。相同规范化摘要表示内容相同，权限与任务批准仍以记录为准。
- 旧登记中的“文件字节 SHA-256”保留为历史原始字节凭据，不与规范化摘要直接比较，也不改写成新算法的历史确认。新版本使用当前[版本登记](agents/versions.json)，登记时间、版本、批准状态、摘要和接收状态；每次变更前后凭据在岗位登记追加保留。
- 下发者正式任务 ID 优先从当前执行环境 CODEX_THREAD_ID 获取，再与会话元数据或任务工具核实；接收者 ID 必须与岗位登记一致。无法核实时保留草稿，不标记人工校验通过、不发送；工具未提供消息 ID 时可用任务 ID、回合 ID、工具调用 ID 和时间关联，注明字段缺失。
- 创建、校验、发送、结果、接单分别读取当时系统时钟，保存 Asia/Shanghai 的带时区时间；工具仅提供调用起止时间时如实记录区间。历史更正注明原记录、证据来源、确定的事实和仍未知的部分；不得用推算时间冒充实际事件时间。当前摘要字段可指向更正条目，原派工及回复保持不变。

## 交付资料归档

需求与设计使用 docs/requirements，每项功能优先用一份文档包含需求、交互与验收；项目总进度使用 docs/progress.md，仅保存索引和跨任务摘要；完整派工、执行反馈和验收证据保存到 docs/tasks/ 对应任务文件。开发说明在所属工程，审核和测试结论记录在对应任务交付报告中，由任务文件保存报告位置和结论，总览只链接任务文件。

## 派工单与编号

- 一项可独立交付的任务一份文件，按[标准模板](tasks/TEMPLATE.md)创建。只有项目经理负责分配编号、维护总览和任务记录；执行 Agent 通过任务消息反馈，不并发写总览，也不自行分配编号。
- 新编号为 `TASK-YYYYMMDD-NNN`，日期取 Asia/Shanghai 当天，NNN 从 001 递增，补足三位（超过 999 则自然增加位数）。项目经理核对全部任务文件（含已完成／取消），先创建文件占用编号，再登记索引和下发；存在同名文件不得覆盖，取消的编号不得复用。一个项目只有当前根项目经理分配编号，多个工作副本不能独立分配。
- 已有任务编号保留不改号；新任务可关联已有编号作为父任务。
- 每次派工序号为任务内 D001、D002 递增；补充、返工、转派及重试保留任务编号并追加序号。可独立执行的新交付项另建任务并关联原编号；审核、测试分别派工时各用独立任务，便于并行跟踪。
- 任务文件位置稳定，完成或取消后保留原路径，状态变更追加依据；索引中的当前状态可更新，原派工与反馈不得重写。

发送前必须逐项人工校验，通过后才允许从草稿改为待发送：

1. 模板必填字段均已填写，编号与文件名一致且唯一；无依赖／不适用须说明，未确定接收人和未替换占位符不能发送。
2. 接收岗位、正式 Agent ID 与岗位登记一致；同岗位没有未经安排的并行执行，路径与允许修改范围符合其岗位权限及本任务授权。
3. 输入、代码及需求版本明确、接收方可访问；未提交内容提供可核对差异来源。正式业务任务必须满足已确认需求和锁定规格的前置规则。
4. 依赖编号存在且达到所需状态，无自依赖或循环依赖；前置未满足的任务只能作为排队预告，不能发送开工指令。
5. 交付物、验收条件、验证方法及通过标准具体可检查；预计时间未知须写原因和再次估算节点，反馈节点不得为空。
6. 完整拟发送内容与任务记录一致，含任务编号、派工序号和记录位置；保存校验者与校验时间。发送结果与接单证据之后追加，不预填成功。
