# 微信审查与交付规则

规则版本：WX-REVIEW-V1-20260915。

适用：微信工程代码、配置和文档的指定版本审核、复审及交付核对。审核职责和写入边界以[审核岗位配置](../../../docs/agents/reviewer.md)及派工为准；本文件不授予审核岗位修复实现的权限。

## WX-REVIEW-01 审查顺序

1. 核对任务范围、当前阶段、被审提交或基线加差异、开发说明、自检和已知风险；确认材料对应同一版本。
2. 对照需求、交互和验收条件判断是否解决问题、是否扩大范围；业务改动核对工程规格引用和契约版本。
3. 对照[架构](../../ARCHITECTURE.md)检查目录职责与依赖、统一请求入口、客户端与服务端责任边界。
4. 按[开发规则](development.md)检查实现，按[测试规则](testing.md)检查验证是否匹配改动风险。
5. 核对源文件、配置、契约副本、运行说明与交付报告是否一致；区分已实现、自动覆盖、人工检查和未验证项。

## WX-REVIEW-02 实现检查清单

| 范围 | 核对事项 |
|---|---|
| 类型与组织 | 外部数据是否校验、类型是否明确、职责是否重复或混杂，是否通过全局状态/工具层绕过边界 |
| 页面与组件 | 加载、空数据、错误、权限受限及重复操作状态是否符合已确认交互 |
| 生命周期与异步 | 资源是否清理，旧请求是否覆盖新状态，退出后的结果是否仍错误更新页面 |
| 接口 | 是否遵循锁定契约、区分传输成功与业务成功，错误映射、超时、重试和重复提交处理是否合理 |
| 平台能力 | 是否经封装使用网络、授权、存储等能力，拒绝/取消/不可用是否有处理 |
| 权限与数据 | 是否误信客户端判断，是否泄露密钥或会话数据，缓存是否可能跨用户误用 |
| 日志与注释 | 关键错误是否可定位，是否含敏感信息或重复噪声，注释是否说明职责且符合实际实现 |
| 构建与依赖 | 是否修改了生成文件，依赖和锁文件是否一致，环境条件与实际验证是否明确 |
| 测试 | 是否遗漏边界、失败、响应乱序和权限场景，静态规则是否有正反例，是否以模拟/编译代替真实验证 |

按获派范围选择适用项，不把没有业务、没有实际账号环境本身写成架构缺陷；相关基础能力缺证据仍须如实指出。

## WX-REVIEW-03 问题判定与整改

- 问题必须给出文件或需求位置、触发条件、预期与实际差异、影响和修复方向；不以模糊猜测阻断交付。
- 区分实际缺陷和可选建议，不因个人格式偏好要求无关重写；自动检查通过不替代业务符合度检查。
- 审核报告给出通过／需整改／阻塞，列出已检查范围、证据与剩余风险。环境缺失写未验证，不虚报通过。
- 报告反馈项目经理，由其安排开发整改；审核不直接修改业务代码、需求或放宽测试。
- 意见有正确性争议时按[部门流程](../../../docs/workflow.md)保存双方依据、请求用户裁决并暂停争议项放行，不由审核或项目经理自行裁决。

## WX-REVIEW-04 复审与完成标准

- 复审读取原问题、整改说明和最新差异，逐项核对修复及相关验证，记录对应版本；受影响实现变化后不自动沿用旧结论。
- 完成条件：符合范围和验收、已知整改项有处理结果、适用验证有证据、必要文档同步、剩余风险和未验证项明确。
- 必需验证缺失时标为实现完成但验证未完成；不能用自检代替独立审核或测试，也不能代替用户最终验收。
- 报告保存于派工指定位置，历史证据保留；新的整改或复审使用新记录，不覆盖旧结论。
- 提交、上传、推送、发布分别依用户授权执行，审核通过不自动授权这些操作。

## WX-REVIEW-05 规则变更与例外

- 规则调整说明原约束、变更依据、影响范围和替代验证，在权威文档同步；不能只在实现中加入豁免。
- 临时例外明确适用任务、原因、退出条件和补验安排，不以全仓忽略代替定点处理。
- 新规则尚未接入自动检查时，在[质量状态](../quality.md)写明人工审核范围；不将规范存在当成工具已执行。
